# 后续内容待确认清单

原则：先列出材料，由项目负责人和相关成员确认范围，再加入展示库。未勾选项表示尚待确认，不表示禁止公开。

## 项目与团队

- [ ] 比赛正式名称、举办时间、主题与可公开的比赛页面。
- [ ] 团队名称及每位成员希望使用的公开署名。
- [ ] 主程序具体负责的模块、合作实现的部分，以及适合展示的技术难点。
- [ ] 如果提到名次、奖项、评分或玩家数据，提供可核对的依据；没有就不填写。

## 图片与视频

- [ ] 允许展示的 Logo / 封面，是否需要额外署名。
- [ ] 3 张当前版本实机截图：探索画面、一个小游戏、非剧透场景或演出。
- [ ] 一段 30–60 秒玩法视频，确认是否包含获准公开播放的音乐 / 音效。
- [ ] 是否允许展示角色、场景和 CG；是否有需要避开的结尾或谜题答案。
- [ ] 分享封面图，确认后放入 `media/` 并在 GitHub 设置中使用。

截图与视频应来自实际游戏。不要把未完成的设计稿或旧版验收截图标为当前成品。

## Windows v1.2.1 下载包

- [ ] 确认现有包对应的源码版本，是否包含准备公开版本的最终修复。
- [ ] 在 Windows 上解压启动，检查完整流程、音频、暂停和继续存档。
- [ ] 确认美术、音乐、音效与字体允许随游戏成品分发，补齐所需声明。
- [ ] 确认包文件名、版本、支持平台、解压空间和已知问题。
- [ ] 确认后作为 GitHub Release 附件上传，核对下载与校验值，再更新 README 链接。

当前清单不包含上传授权；包体需在确认分发范围后另行加入，不直接提交到 Git 源码目录。

## 网页与其他平台

- [ ] 构建网页版，在最终托管地址验证加载、音频、全屏、鼠标滚轮与存档。
- [ ] 确定网页托管平台、真实试玩地址和允许嵌入 / 分享的范围。
- [ ] 如提供 macOS，确认架构、实际运行、签名 / 公证状态和分发说明。
- [ ] 首页只列实际可用的下载或试玩入口，不提前承诺手机或未测试平台支持。

## 源码与素材

- [ ] 是否公开源码；如果公开，先确认参与成员同意及适用的代码许可证。
- [ ] 哪些模块 / 片段可以放，是否需要移除内部信息或第三方内容。
- [ ] 原始图片、动画、音乐和字体是否允许作为独立原文件再分发。
- [ ] 确认“允许放进游戏”与“允许上传素材原文件到公开仓库”是否有不同限制。
- [ ] 不导入私密开发库的旧提交历史、内部日志、私人联系方式或授权邮件。

## 发布与主页展示

- [ ] 补好最终署名和必要的内容使用说明；不擅自给全部代码与素材套统一许可证。

- [ ] 发布确认过的游戏包或网页入口，再添加真实链接。
- [ ] 在个人 GitHub 主页的 `Customize your pins` 中置顶本库。
- [ ] 如有个人主页 README，加入项目简介与本库链接。
